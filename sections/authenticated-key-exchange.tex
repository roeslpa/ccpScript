\section{Authenticated Key Exchange}
\label{sec:AKE}

Using a Key Encapsulation Mechanism~(KEM), two parties can easily establish a fresh symmetric key.
With the forward secure construction from Section~\ref{sec:forward-sec}, the fresh symmetric key even remains secure if the receiver's decapsulation key is ever corrupted.
Since this construction is based on Hierarchical Identity-based Encryption~(HIBE), it suffers from impractical performance limitations.
Furthermore, neither a KEM nor its forward secure extension offer any authenticity guarantees for the receiver:
The receiver does not even know who established the key with them.

In this section, we begin with adding interaction between the two parties to \emph{efficiently} achieve forward security;
in a second step, we extend the result to also provide authenticity.
Thus, after the key exchange, both parties can be sure that their communication partner is indeed the intended party and that no other party has knowledge of their shared symmetric key.

\paragraph{Key Exchange with Interaction} 
Consider the \emph{key exchange with interaction}~(IKE) protocol from the exercise. 
As a reminder, the protocol (here called two-pass key exchange) is defined as follows:

A Two-Pass Key Exchange $\TKE=(\TKEsnd,\TKErsp,\TKErcv)$ is a tuple of three algorithms with state space~$\stsp$, initial ciphertext space~$\csp_I$, response ciphertext space~$\csp_R$, and symmetric key space~$\ksp$:

\begin{itemize}
    \item $\TKEsnd: \emptyset \tor \stsp\times\csp_I$
    \item $\TKErsp: \csp_I \tor \ksp\times\csp_R$
    \item $\TKErcv: \stsp\times\csp_R \to \ksp$
\end{itemize}

A protocol execution can be seen in Figure~\ref{fig:tke:overview}.
This protocol can be based on a standard KEM by embedding a freshly generated encapsulation key in the first ciphertext from Alice to Bob, and embedding the KEM ciphertext to this encapsulation key in the response.

The problem with a two-pass key exchange is that it is vulnerable to a \emph{Person-in-the-Middle} attack, where the adversary~$\advA$ intercepts the messages between Alice and Bob and replaces them with their own messages (and therefore their own keys)~(Figure~\ref{fig:tke:MitM}).

\paragraph{Key Exchange with Authentication} To prevent this and to provide actual authentication, we use \emph{Authenticated Key Exchange}~(AKE) protocols.
An authenticated key exchange $\AKE=(\AKEgen,\allowbreak\AKEsnd,\allowbreak\AKErsp_R,\allowbreak\AKErsp_I,\allowbreak\AKErcv)$ is a tuple of five algorithms with secret key space~$\sksp$, public key space~$\pksp$, state space~$\stsp$, ciphertext space~$\csp$, and symmetric key space~$\ksp$:
\begin{itemize}
    \item $\AKEgen: \emptyset \tor \sksp\times\pksp$
    \item $\AKEsnd: \sksp\times\pksp \tor \stsp\times\csp$
    \item $\AKErsp_R: \sksp\times\csp \tor \stsp\times\csp$
    \item $\AKErsp_I: \stsp\times\csp \tor \ksp\times\csp$
    \item $\AKErcv: \sksp\times\stsp\times\csp \to \pksp\times\ksp$
\end{itemize}

\paragraph{Correctness (informal)}
An $\AKE$ protocol is correct if Alice and Bob compute the same key $k$ for every honest protocol execution.

\paragraph{Security (informal)}
The adversary has access to the following oracles.
With these oracles, the adversary can generate new parties' key pairs and start sessions between parties.
To participate in a session, each party has a dedicated instance that executes the respective key exchange algorithms.
In every terminated session, a key is established.
For such keys, the adversary can query oracle $\Ochall$ that outputs either the real key established in a session (if challenge bit $b=0$) or a random key (if $b=1$).
The adversary terminates with a guess~$b'$ for challenge bit~$b$.

\setlength\itemizeskip{3.5cm}
\begin{itemize}
    \item $\Ogen() \to \pk$:\hfill\makebox[\linewidth-\itemizeskip][l]{Generate a new party's long-term key pair}
    \item $\Osnd(i, s, \pk) \to c$:\hfill\makebox[\linewidth-\itemizeskip][l]{Lets instance $s$ of party $i$ start a session with the party who owns~$\pk$}
    \item $\Orsp(i,s,c)\to c'$:\hfill\parbox[t][][l]{\linewidth-\itemizeskip}{Lets instance $s$ of party $i$ respond to $c$; also used for final receipt}
    \item $\Ocorrupt(i)\to\sk_i$:\hfill\makebox[\linewidth-\itemizeskip][l]{Corrupts party $i$'s long-term secret key}
    \item $\Oreveal(i,s)\to k_{i,s}$:\hfill\makebox[\linewidth-\itemizeskip][l]{Reveals final session key computed by instance $s$ of party $i$} 
    \item $\Ochall(i,s)\to k_{i,s,b}$:\hfill\makebox[\linewidth-\itemizeskip][l]{Either outputs real or random session key of instance~$s$ of party $i$}
\end{itemize}

\paragraph{Trivial winning conditions}
The trivial attacks are listed in Figure~\ref{fig:ake:trivial}. 
Note that the names of the trivial attacks give the general strategy and that the provided pseudocode can sometimes be changed (e.g., by switching the order of $\Ochall$ and $\Oreveal$ in the first attack).

The third attack, in particular, requires only that $\pk_j$ is the intended partner of $(i,s)$ and that $(i,s)$ has no session partners;
thereby, while the concrete Attack~3 in Figure~\ref{fig:ake:trivial} only covers a corrupted responder in a session, the attack is also trivial if the initiator of the session is corrupted.
Nevertheless, an attack in which the corruption only happens \emph{after} the session terminates is non-trivial and, therefore, permitted.
By permitting it as a non-trivial attack, our definition covers forward security.

An attacker against an~$\AKE$ is only considered successful if neither of the listed trivial attacks is performed.
Based on this, our informal security definition requires a secure $\AKE$ to provide authenticity and forward security.

\paragraph{Session partners}
To formalize Trivial Attack~2, the concept of \emph{session partners} must be defined. 
In literature, however, there are different variants for this concept, which can be summarized as follows:
\begin{itemize}
    \item \emph{Matching Conversations} \cite{C:BelRog93}: ``Both instances saw the same transcript''
    \item \emph{Session identifiers} \cite{STOC:BelRog95,EPRINT:BCJSW24}: ``Both instances saw the same relevant parts of the transcript''
    \item \emph{Original Key Partnering} \cite{EPRINT:LiSch17}: ``Using the same randomness, $(i,s)$ and $(j,t)$ would have computed the same key in an honest execution''
\end{itemize}
A more detailed discussion of the advantages and disadvantages of these concepts, as well as a systematization of security definitions for authenticated key exchange can be found in~\cite{RSA:PRSS21,EPRINT:BCJSW24}.
This lecture uses the \emph{Matching Conversations} definition when talking about session partners.

\paragraph{Constructions}
We present two constructions of authenticated key exchange protocols.
Both constructions provide forward security.
The first one (Figure~\ref{fig:ake:signed_dh}) is based on an ephemeral Diffie-Hellman key exchange and uses signatures to provide authenticity.

The second AKE construction (Figure~\ref{fig:ake:kem}) uses a KEM and a multi-key PRF (Figure~\ref{fig:prf:multi_key:ind}). 
This construction provides forward security \emph{and} authenticity via the security of the underlying KEM.
To see how this is achieved, we highlight the secrets that can be learned by the adversary~$\advA$ after corrupting Alice and Bob in orange and blue, respectively, in Figure~\ref{fig:ake:kem}.
For example, after corrupting Bob and learning the secret key $\sk_B$, $\advA$ can decapsulate~$c_1$ (which can be learned by eavesdropping on the communication) and obtain $k_1$.
The symmetric key $k$ will still remain secure, since $k_3$ will not be known to~$\advA$, even if both Alice and Bob were corrupted.
The reason for this is the usage of fresh keys $\sk',\pk'$ for each new execution.

\subsection{Real-World Authenticated Key Exchange}
The list of AKE protocols deployed in practice is very long: TLS, SSH, IKEv2 in IPsec, X3DH and PQXDH in Signal, Noise with Wireguard, etc.
In this section, we focus on three relevant, very different examples:
TLS, which is the most important protocol for establishing secure channels on the Internet,
the Noise protocol framework, which offers a lightweight alternative for special deployment scenarios,
and X3DH, which is a fast key exchange protocol for settings in which the two communication partners do not need to be online simultaneously.

\subsubsection{Transport Layer Security~(TLS)}
The key exchange in TLS~\cite{rfc8446} resembles the signed Diffie-Hellman construction in Figure~\ref{fig:ake:signed_dh}.
However, since TLS offers many different modes and a dynamic negotiation of used cryptographic algorithms, the schematic overview of the cryptographic core of TLS in Figure~\ref{fig:ake:tls} can only be considered a strong simplification.
For more details we refer the interested reader to the large literature on security analyses of TLS~1.3~\cite{JC:DFGS21,JC:DieJag21,EC:DDGJ22,AC:BDEFKK22}.

\subsubsection{Noise Framework}\label{sec:NoiseFramework}
The Noise framework \cite{NoiseFramework} is a set of rules to combine Diffie-Hellman key exchange with Authenticated Encryption~(AE) to establish a secure channel.
Instead of implementing dynamic algorithm and protocol negotiation as in TLS, the Noise framework offers multiple different static protocols for different settings.
Thus, such static Noise protocols are meant to be deployed in settings in which all protocol participants can be pre-configured equally.
Besides avoiding dynamic negotiation, this homogeneous pre-configuration allows for a more efficient and lightweight protocol design.

Protocols from the Noise framework are used by WhatsApp for its client-to-server communication and by WireGuard among others.
Dowling et al. \cite{PKC:DowRosSch20} and Angel et al.~\cite{CCS:ADHSW22} provide a deeper analysis of the Noise Framework.

One protocol defined in the Noise Framework is ``NK''. 
Following the naming convention of Noise protocols, the ``N'' means that the initiator of a protocol execution has \textbf{n}o static public key and the ``K'' means that the responder in a session has a static public key \textbf{k}nown to the initiator.

In the documentation of the Noise Framework, the protocols are described in a format similar to the one in Figure~\ref{fig:ake:noise:nk}.
Figure~\ref{fig:ake:noise:nk_overview} gives an overview of the protocol execution in the format used in this script.
The~s in the figure is the static key of the responder, which is transmitted to the initiator before the protocol begins (shown by the dots afterwards).
An~e is an \emph{ephemeral} key (short-lived key) that correspond to a DH public key-share (e.g. $g^x$).
If two letters are combined a Diffie-Hellman key exchange with the two keys is performed, e.g.~es for $g^{x\sk_B}$.

The messages sent during and after the protocol execution offer different levels of security: 
The encryption of $m_1$ offers forward security for the sender but not for the responder, while authenticity is only guaranteed for the responder.
Anonymity is guaranteed for both parties, but for the responder this holds only as long as their long-term secret key is not corrupted.
For $m_i, i\geq 2$ the encryption offers forward security for both parties, while the other security guarantees remain unchanged.

\subsubsection{X3DH}
\label{sec:AKE:X3DH}
The X3DH~\cite{X3DH} protocol is an extended and authenticated 2-pass key exchange. 
It is designed for asynchronous settings, where two parties want to establish a shared secret key, but one of them might be offline.
For this, one party (here named Bob) stores his long term public key~(LTK) at a server.
Furthermore, Bob regularly renews and sends ephemeral Diffie-Hellman public keys to the server: a signed prekey and a set of one-time keys.

If Alice, then, wants to establish a shared symmetric key with Bob, she can fetch Bob's public keys from the server.
She also generates an ephemeral Diffie-Hellman exponent, which is then combined with Bobs keys and used to derive the symmetric key through a PRF. (Figure~\ref{fig:ake:x3dh}).

If all of Bobs one-time secret keys were used, and he has not renewed them yet, input~$g^{ab}$ is not part of the final key computation.
This minimally reduces the forward security of the protocol, since the prekey is renewed less often.

The X3DH protocol guarantees strong forward security, authenticity and deniability (both parties can deny their participation).
As it works in asynchronous settings, it is used to exchange keys when initiating sessions in messaging protocols (see Section~\ref{sec:rke} on Ratcheted Key Exchange).
